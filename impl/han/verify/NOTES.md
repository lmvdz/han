# han.verify and han CLI: spec gaps and the readings taken

1. **No "ok" in `VerifierStatus`** (han.ts has stopped / faulty / moved only). Added `{state: "ok", through}`. `stopped` is used for "could not continue" (connection, a seq gap, a profile chain unavailable or faulty, caller cancelled); it is never a fault and carries no proof. Proposed: add `ok` to han.ts.
2. **Server keys have no wire source in the generic binding** (`.well-known/han` is not served by han-seq, NOTES.md 5). A verifier is given them explicitly (`--server-key SERVER=KEYFILE|PUBKEY[,keyId]`, or a JSON file). It never learns a key from the server it checks. Key windows `from` are taken as 1970-01-01.
3. **Profile views over the wire.** The verifier reads `profile:<actor>` for every `(actor, seq)` pinned in a receipt (and in a `redactedBy` receipt), verifies those chains with the same Mirror (a profile entry is checked against the profile chain before it), and folds the view itself. `@:S` views are synthetic from the given server keys. Retained in the state file with the space (4.3).
4. **A reader who cannot read every seq cannot verify the chain.** P-02 hides records from former members, which leaves a seq gap. The spec does not say what a verifier then reports; it reports `stopped (seq gap)`, since a gap is not provable misbehaviour. A verifier must therefore be a reader of the whole space (an auditor owner/member, or the home reading as `@:S`).
5. **Fault proof format.** han.ts has `{kind, receipts, record?}`. That is enough for `equivocation` and `future-time` only. Every other kind needs the verified chain before the fault and the profile chains it pins to be replayed offline, so the proof here adds `chain`, `profiles`, `serverKeys`, `through`, `reason`, `observedAt`. The checker replays everything from nothing and demands the same kind of fault at `record`. Proposed: make this the normative proof shape. The proof carries message content of the space (a private space's proof is private); stripping content is not possible without losing the content-hash check.
6. **Trust in a proof's keys.** `verify proof` uses the server keys bundled in the proof only when no `--server-key` is given, and says so. A proof is only evidence against a home if its offending receipt is validly signed; if it is not, the check still reports the record fails but says the fault is the delivery's, not provably the home's.
7. **`future-time` cannot be checked offline.** It depends on the verifier's clock when it saw the receipt. The proof records `observedAt` (the verifier's clock) and the checker accepts when the receipt is dated beyond `observedAt` + 300 s; that trusts the prover's clock. The skew (300 s) is not in the spec (7.5 says only "flag receipts dated in the future"). A fault in a *profile* chain makes the space `stopped`, not `faulty` (its proof sits under the profile space's own status).
8. **Mirror reason strings drive the fault kind.** `wire.Mirror` returns free text; `chains.classify` maps it to a kind by phrase (header/content/seq/prev/time/profile-regression = `chain`; entry or receipt signature = `bad-signature`). han.ts lists eight kinds but no reason codes. Proposed: Mirror returns the kind.
9. **Head gossip transport.** R-15 describes `hello`/`read` knownHeads between a verifier and a server. Between two verifiers it names no channel, so verifiers signal their head in the space (`{type: "heads", heads: [receipt]}`, G-04: only readers receive it) every `--gossip-interval` (default 600 s, R-15's bound) and announce faults as `{type: "fault", proof}` (R-14, T-05). A receiver adopts a fault only if the proof checks against its own trusted keys. A sequencer that drops these signals defeats the room channel (not out-of-band exchange via `Verifier.observe`). The sequencer's own `heads` item in `read` is compared too, so a server that shows one reader two histories over time is caught without peers.
10. **Equivocation `through`** is `seq - 1`: nothing at or above the conflicting seq is trusted.
11. **Moves.** A verified `space.move` makes the status `moved` (to the target); following the new home is not implemented (no federation in han-seq).
12. **Redaction.** When a `redact` record verifies, the verifier deletes the target's content from memory and rewrites its state file (P-12); the redacted record still verifies through its `redactedBy` proof on reload.
13. **CLI.** `han approve` prints the plan and checks `sha256(JCS(plan)) = planDigest` before signing (P-08) but does not ask for a keypress (the explicit command is the confirmation). `session release` sets `seen` to the head just read (override `--seen`), since P-15 denies a release that predates an outside instruction. Ids may be unique 8+ hex prefixes.
