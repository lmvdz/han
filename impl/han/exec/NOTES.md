# han.exec notes: spec gaps and the readings taken

1. **Plan shapes are not specified (§5, han.ts `Plan`).** `file.write`: `target` = path relative to the sandbox, `args = {content: str}`. `http.post`: `target` = URL, `args` = the JSON body. `argsBlob` is not supported (the plan is refused, never claimed).
2. **What the executor refuses before claiming.** A plan that is redacted or does not hash to `planDigest` (X-09), an action not enabled, a path outside the sandbox or a URL outside the allow-list is never claimed (otherwise a failed/no outcome would rearm the effect and loop). X-09 says "before launching"; checking before the claim is stricter and avoids claims that can only fail. The spec does not say what to do with an effect the executor will never run: it stays `ready` forever (a proposer or owner cancels it).
3. **X-04 order.** `launching` is journaled, then the deadline is checked (`elapsed < window - stallBound`), then the launch. A claim that fails the check has both `launching` and `expired` events, so X-05's "`started: no` only if `launching` was never journaled, or `expired` follows it" holds. The platform duty "no more than stallBound between check and launch" is not enforced: the launch is the next statement, but a thread pool hop sits in between.
4. **X-02 clock.** The reading is taken just before the journal write that precedes the first send, so it is slightly earlier than the true first send (conservative). `time.clock_gettime(CLOCK_BOOTTIME)` where available, else `time.monotonic`; on Windows that is QueryPerformanceCounter-based, whose suspend behaviour Python does not document, so "counts through suspend" is not verified there.
5. **X-06 outside lookup.** "Look the result up in the outside system if possible" has no defined interface; none is implemented. A `launching` claim without a journaled result is always reported `unknown/unknown`. The executor journals the action's own result (`ran`) before reporting; a claim with `ran` is reported with that result (`started: yes`), which is what the journal proves. A crash between the action and the `ran` write is therefore `unknown`.
6. **Re-claiming after `failed/no`.** After a `failed/no` report P-09 rearms the effect (approval returned), so the executor claims again (attempt+1) right away, in the same or the restarted process. There is no back-off and no attempt limit; a permanently slow link would loop. The spec has no cap.
7. **X-10 when the launch is unproven.** If the executor's outcome is refused because an owner abandoned, it resolves `succeeded`/`failed` from the journal's `ran` result, or `failed` if it provably never launched (no `launching`, or `expired`). If it launched without a journaled result it cannot make a true statement and journals `unresolved`; an owner has to resolve (P-10). The spec says "MUST report what really happened" without covering this case.
8. **Cost.** Reported as `{unit, amount: 0}` only when the effect carries a cost in a budgeted space (a reservation exists), with `started: yes`; otherwise omitted (P-06: allowed only within a reservation).
9. **X-07 marker.** A marker file `<keyfile>.used` records the journal's uuid. Journal missing + marker present, or marker uuid ≠ journal uuid, or journal belonging to another keyId: refuse. This only protects a key copied together with its marker; a key copied alone to a new machine starts a new journal. The spec cannot be enforced stronger without a server-side record of instances (an idea: `key.add` per instance and a server-visible "first used" claim).
10. **Instance key = actor key file.** `--key` is both the signing key and the instance key; `--instance` must equal its keyId. The spec allows several keys per actor, one per running instance.
11. **Feeding.** The executor reads the full state (`read … state=true`) after each record and acts on `effects[*].phase == ready` naming it; `subscribe` is only a wake-up. History is not replayed (it subscribes after the head it reconciled at).
12. **Held agents (P-15).** Nothing special in the executor: the server keeps a held agent's effects in `awaiting-approval` until the guard approves, and E3 checks the guard's approval at claim.
13. **The outcome entry is journaled signed (`reporting`) before it is sent**, so after a restart the same entry is re-sent (dedupe) rather than a second one being made.
14. **Shared-code need:** `pyproject.toml` `[tool.setuptools] packages` should list `han.exec`, and a `han-exec = "han.exec.__main__:main"` script. Tests run from `impl/` without it.
