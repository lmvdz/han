## Findings, ranked by effect on beta users

1. **P1 — Build the guided repository-scoped Trusted team journey.** This remains the largest product gap. Current task intake helps an already configured operator, not a fresh teammate. Guide installation, sign-in, team creation/join, repository selection and first work, with resumable setup and an explicit grant preview. Automatic landing needs genuine owner-granted authority bounded to selected repositories and required checks, not a UI label or bypass of existing approval rules. Preserve the advanced path; an agent must not widen its own grant. Align normative authorization and conformance tests before claiming the preset works.

2. **P1 — Verify the final admission fix under the actual service identities before calling startup reliable.** The latest deployed run returned NOT CONFIRMED while the agent actually worked because a `0600` admission file was unreadable by the node. `HostAdmission::write` now applies `0640`, and the host propagates write failure. The production unit uses `UMask=0077`, so this is a relevant correction. The retained Windows registry test does not execute the Unix permission assertion. Verify the rebuilt binary with the actual node group, both admission/refusal receipts, and unwritable receipt failure. Preserve the live session already in progress; an unconfirmed start is not permission to launch duplicate work.

3. **P1 — Make failed and uncertain work recoverable through the TUI.** The new task flow keeps known task IDs and suppresses automatic uncertain retries; this is useful progress. However, `task_rows()` only exposes open tasks. The failed second attempt closed its task, and the operator had to diagnose it and create an explicitly related follow-up. Provide a visible failed-task reason, preserved-work location and deliberate follow-up action that retains the original task relationship. Then test host/node/executor restart, lost replies, conflict, failed/missing checks and quota exhaustion with real harnesses, without database edits or private recovery scripts.

4. **P2 — Resolve misleading overlap and trust/usage presentation.** The retained live evidence again reports a no-issue session overlapping an old issue-5 session. Reproduce and fix that before asking a team to rely on coordination badges. The driver declares prompt-only gating, while the TUI status line exposes sandbox fidelity rather than a separate gate field required by `han.status/1`. Show outer sandbox enforcement and tool-gate limits distinctly. Represent subscription cost as unmeasured rather than a bare zero. These are presentation/evidence gaps, not demonstrated sandbox escapes.

5. **P2 — Complete independent acceptance with unfamiliar users.** Run the fixed setup journey through a real landed change, measuring the 10-minute first-task and 5-minute join targets with ordinary HAN setup included. Two people on separate machines should identify work, steer, resolve a blocker and inspect the result from the TUI. The historical single-operator landing, controlled test fixtures and direct mount reproductions do not substitute for this. The two-week M6 observation remains unverified and separate from these shorter acceptance checks.

## Release blockers and historical defects

No current-source authority escape, silent work loss, credential disclosure, falsely completed task or silent uncertain-effect replay was established in this review. This is a bounded conclusion, not an exhaustive security certification.

The proposed runtime-executing doctor implementation had a real privilege flaw: a writable harness record could select a program for root to execute. It was corrected before the final #176 implementation assessed here. Current code calls fixed `/usr/bin/test` through fixed `/usr/sbin/runuser` when needed, uses actual identity checks, clears the environment, discards utility output, and skips unsupported platforms. It tests file-access prerequisites, **not executable integrity, Node version, or runtime compatibility**.

The old supervisor success-without-admission path also lacked supporting evidence. Current code requires an explicit admitted receipt or returns an unconfirmed/failure result. The deployed permission problem is operationally serious but did not falsely report success: the start was marked unconfirmed. An admitted receipt still means preliminary admission, not completion of checkout and harness initialization.
