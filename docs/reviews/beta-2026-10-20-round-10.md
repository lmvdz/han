## Implementation findings

The TUI now treats `can_approve` as a review-candidate hint rather than an authorization decision. List and card text defer eligibility to the home. A shared application helper blocks signing when `NodeStatus.headless` is explicitly true, both before opening the signing panel and immediately before submission. A late headless update also removes the signing footer’s Enter affordance.

This correction preserves existing home enforcement and cancellation behavior. It does **not** implement complete eligibility evaluation. Existing guest/proposer filtering and `needs_me` hints remain heuristic, as the updated specification explicitly acknowledges. Those limitations can omit legitimate candidates or suggest attention from someone whose approval would not count.

MCP instructions now correctly state that:

- Policy determines authorization; eligible Trusted-team changes may proceed automatically.
- A proposal ID is not evidence of execution or landing.
- Sandbox, login and network access depend on the configured backend and driver.
- Local toolchains may permit builds and tests, but local results do not replace the lane’s required checks.

The bubblewrap diagnostic no longer labels every probe failure as inability to create namespaces. When the error names permission denial for the executable, it recommends an accessible installation location while preserving private-directory restrictions. Admission behavior is unchanged.

No new correctness defect was demonstrated in these changes.
