## What changed and what the evidence supports

`trusted_team_policy` grants `vcs.land` with `proposer: true`, an exact repository and `maxTier: 1`, then installs a human-owner fallback. The preset is invite-only, requires confirmed operators, and keeps ordinary changes above 500 lines, incomplete summaries and built-in sensitive paths out of its automatic grant. It does not silently authorize other repositories or other actions. Executor-required checks and the final policy claim remain mandatory.

`SpaceCreateTrusted` publishes one complete `space.create` policy, avoiding a temporarily broader create-then-edit policy. The command is a face operation requiring presence, and host RPC cannot invoke it. An offline creation returns a queued result and later delivers that same policy. TUI setup displays a grant preview and saves recovery information before sending; if that save fails, nothing is sent. Unknown/queued responses do not trigger automatic resubmission. CLI lost-reply guidance now warns that another `--apply` creates another space. The stored marker is ordinary preferences data, not an operation-level deduplication token or a guarantee across corrupt preferences, power loss or competing TUI writers.

PR 179 addressed a real security finding during review: a proposer-authorized lane could push a branch and start CI before a missing guard was checked by the final claim. The current `effectReady` path uses the home's actual profile pinning and Policy decision. The lane checks readiness before preparation, pushes, PR creation, check starts and reruns, including restored work and revocation during a check poll. Refusals remain visible as waiting reasons. Readiness is explicitly point-in-time: it reserves no budget, consumes no approval and is not atomic with subsequent policy changes. A final claim is still required. Evidence-dependent approval rules must use existing evidence or a separately authorized try rather than waiting for their own lane to produce the evidence.
