# HAN wire conformance vectors

What a server must put on the wire, as frames. Built from the transcripts in `interop/golden/` (D15 of `interop/DECISIONS-r21.md`): every operation file is something **both** reference servers (Python `impl/`, clean-room TypeScript `cleanroom-ts/`) answered byte for byte alike for both clients. The rules they pin are architecture.md §2, §3, §4.1, §4.3, G-01…G-11.

```
python ref/run_wire_vectors.py --url ws://127.0.0.1:8787/han     # a server already in test mode
python ref/run_wire_vectors.py --launch py | ts                  # start a reference server in test mode, run, stop it
python ref/run_wire_vectors.py --check                           # offline: the files are well formed and self-consistent
```

## How a server passes

1. Start it in **test mode** with an empty data directory (G-11): ServerName `a.localhost`; a **test clock** (wall time `2026-01-01T00:00:00Z` and steady time 0 at the start; neither moves except by the control call `test.clock` of G-11, so until a vector moves it every `receipt.time` is that instant and every `homeSig` is reproducible); the server key of `config.json` (`keyId` `h1`, `from` `1970-01-01T00:00:00Z`, private key = `sha256(UTF-8 seed)`); the profile spaces of `config.json`'s actors provisioned (`@alice`, `@bob`, `@carol`, `@vera` human, `@x` service, key `k1` each). How a server is put into this mode is its own business (flags are not specified). `interop/py_host.py` and `interop/ts_host.mjs` are two examples (they also provide `test.clock` and `test.limits`), and `--launch` uses them. A server that does not provide `test.clock` fails the vectors that move the clock (`T1`, `R16`, `R03a`, `V57`), and one that does not provide `test.limits` the vectors that lower the frame limit (`T2`, `H3a`), nothing else. The stock CLIs have no test clock (`python -m han.seq` has `--register` but no clock option; `node dist/seq.js SERVER DIR PORT` provisions nobody), so they fail every receipt `time` and `homeSig`.
2. Run the runner against its URL. **A server passes when every vector passes**: each `expect` step matched the next frame on its connection after the masking below, and no frame arrived that no step expected.
3. Run once per fresh server: the operation files build on one another (seq numbers, ids), in the order of `index.json`; the probe files follow.

Vectors never depend on the server's key beyond the config: `check` verifies that every client entry is validly signed, every receipt in the files carries a valid `homeSig` under the config key, the 18 receipts of `s1` form one chain, and every record's entry id matches its receipt.

## Format `han-wire-vector/1`

An operation file is one vector `{format, name, description, rules, steps}`; a probe file is `{format, kind, note, vectors: [{id, title, expect?, rules?, source?, steps}]}`. `steps` run in order. Every step except `http_get` names a connection with `conn`:

| Step | Meaning |
|---|---|
| `{conn, send: Frame}` | write the request frame as one text message (after placeholder expansion, below) |
| `{conn, send_raw: "text"}` | write this exact text message (used for frames that are not valid requests) |
| `{conn, send_binary: "hex"}` | write a binary message |
| `{conn, expect: Frame}` | the **next** message on that connection must be a text frame equal to this one (matching below) |
| `{conn, expect_close: true}` | the connection must be closed by the server (a close frame or end of stream) before the timeout |
| `{conn, expect_silence: true}` | no message arrives for `silenceMs` (400 ms) |
| `{http_get: "/path", expect_status, expect_type, expect_json}` | `GET` on the HTTP(S) origin of the WebSocket URL; the body is I-JSON equal to `expect_json` |
| `{clock: {wall?, steadyAdvance?}}` | calls `test.clock` (G-11) on the runner's own connection (authenticated as `@alice`, not one of the vector's) and expects `ok: {wall, steady}`: the wall reading as set (or as it was) and the steady reading as it was plus `steadyAdvance`. The runner keeps the readings across the vectors of one run (a fresh server starts at the config clock, steady 0). One expectation. A vector that sets `wall` puts it back before it ends |
| `{limits: {maxFrameBytes?}}` | calls `test.limits` (G-11) on the runner's own connection, like `clock`, and expects `ok: {maxFrameBytes}`: the value set (or, for `{}`, the one in force). One expectation. A vector that lowers it restores 1,310,720 before it ends; while it is lowered the runner also fails any server frame longer than the lowered value |
| `{conn, generate: {count, head, firstId, space, kind, author, body, content?, nonce}}` | `count` appends the runner builds itself instead of reading them from the file: entry k (from 0) has body and content with `{k}` replaced by k, `seen` = `head` + k, request id `firstId` + k, `nonce` = the first 26 characters of the lowercase base32 of SHA-256(`"wire-vector-nonce-"` + the `nonce` template with k), time = the config clock, and is signed by `author`'s config key. Each reply must be `<receipt seq=head+k+1>`. **None of it is an expectation**: the paging setup is 1,001 appends that only prepare state, and counting them as 1,001 expectations (as round 22 did) overstated what the vectors pin |

**Connections.** A label opens its own WebSocket. A label that is an ActorId (`@alice:a.localhost`) is **authenticated** before its first step with a set-up `hello` that is not part of the vector, unless that label's first step is a `hello` send or the expectation of the Challenge frame; any other label (`raw:1`) stays unauthenticated. Every connection first receives the server's Challenge, which the runner reads and checks (shape: `{challenge, server, versions, time}`, challenge 22–128 characters of `[A-Za-z0-9_-]`); only a step that expects it (`01-hello`, D11a, D12a, D9a) sees it. Messages on different connections are compared per connection, not in global order.

**Frames** are the JSON of the message. Request ids are as written. The runner sends compact JSON (no spaces); servers' text formatting is irrelevant.

**Comparison.** `expect` is equal to the received frame when both parse (I-JSON: a duplicate key, a fractional number or an exponent in the server's text is a failure) to **equal values of equal type with the same members**; that is equality of their JCS bytes, so key order and whitespace do not matter and everything else does, including every hash, signature and time. Before comparing, the received frame is masked:

| Masked | Rule |
|---|---|
| `error.message` | removed from the received frame (free text, never normative). `code`, `movedTo` and `retryAfterMs` stay and must match |
| blob `data` longer than 300 characters | replaced by `<b64u len=N sha256=H>`, `N` the length in characters and `H` the first 16 hex digits of the SHA-256 of the string's UTF-8; the vector holds the masked form |

Matchers (a string value in `expect` that stands for a class of values):

| Matcher | Accepts |
|---|---|
| `<challenge>` | 43 characters of canonical base64url (32 random bytes), D12 |
| `<challenge-shape>` | 22–128 characters of `[A-Za-z0-9_-]` |
| `<receipt>`, `<receipt seq=N>`, `<receipt seq=N time=T>` | a Receipt (exactly its ten members) whose `home` and `homeKey` are the server and key of the config, whose `homeSig` verifies under that key, whose `id` is the id of the entry sent in the request with that frame id, whose `seq` is `N` if given and whose `time` is `T` if given. Used where the exact receipt would pin something the vector does not test (the `profiles` of a setup entry) |
| `<posint>` | a positive integer (the `retryAfterMs` hint of an R-03a `unavailable`: the two reference servers estimate it differently, §4.1 step 7) |
| `<url-of-the-binding>` | a `ws://` or `wss://` URL ending in `/han` (the `sequencer` of `/.well-known/han`) |
| `<profile-bootstrap @actor kind>` | the record (`{entry, content, redacted, receipt}`) that is seq 1 of `profile:@actor` (§4.3): a `space.create` authored by the server actor `@:S`, `keyId` and `homeKey` of the server key, `seen` 0, `refs` `[]`, signed by the server key, body `{policy, profile: {actorKind: kind, key: {keyId, publicKey}}}` with the actor's key from `config.json` (`policy` is any object: the PolicyDoc and the `nonce` are the server's own and differ between the two reference servers), content `{name: <actor>}`, and a receipt for seq 1 with `prev` `""`, `profiles` `{"@:S": 0}` and a valid `homeSig` |

**Placeholders in client frames.**

| In `send` | Expands to |
|---|---|
| `"proof": "<proof>"` in a `hello` | the Ed25519 signature of the `who` actor over `"han-hello-v1\n" ‖ challenge ‖ "\n" ‖ "a.localhost"`, `challenge` being the one this connection received |
| `<proof challenge=X>`, `<proof dialed=Y>` | the same over another challenge string, or another dialed name (the server must answer `denied`) |
| `"data": "<b64u len=N sha256=H>"` in a `blobPut` | the base64url of the next `N*3/4` bytes of the blob generator starting at `args.offset` (byte *i* of a blob is `(i*7+3) mod 251`; `config.json` lists the two blobs by hash). The runner checks that the expansion hashes to `H` |
| `"<repeat c n>"` (a whole string) | the character `c` repeated `n` times |

After a `send` of `subscribe`, `watch` or `read` with `follow`, the runner waits `settleMs` (250 ms) so the registration has happened before another connection acts. A server that registers a follow asynchronously and slower than that is not conforming to G-09 ("atomically with registration").

## Hello, byte by byte (worked example)

## Not yet vectorised

What E10 listed, and what the single-server test mode (one server, a test clock, no second server) cannot show deterministically. A server that implements these is still tested for them by `ref/run_wire.py` (the reference model) and the implementations' own suites, but no wire vector pins the frames:

- **`limit`** (rate limits, §4.1 step 6): the servers' rate limits are their own configuration (a `limiter` in the Python sequencer, `appendsPerSecond` in the TypeScript one, counted in different units), and test mode does not fix one. So the verdict pairs *Policy before the rate limit* (5/6) and *the rate limit before the moment-dependent `unavailable`* (6/7) have no vector.
- **R-08** (`minDurability` the server cannot reach) needs a durability the test mode does not offer. R-16 (early abandon), R-03a (a clock behind the chain) and the verdict pair 5/7 are vectorised since round 23 (`R16`, `R03a`, `V57`, using `test.clock`). The `unavailable` of step 4 (an author's profile on another server that cannot be fetched) needs a second server.
- **Dedupe before routing** (pair 1/2): needs a space that has moved away (`space.move`), i.e. two servers. Dedupe before Policy (1/5) and before shape (1/3: P15) are vectorised (`E5a`, `P15`).
- **Federation**: notices to another server, relayed signals with `from` (only the refusal D10a is vectorised), blob transfer, remote profile reads, `/.well-known/han-peers` with peers.
- **Moves**: `space.move`, `host` beyond the `denied` of D6a, the §7.3 handshake.
- **Key rotation**: `key.add` and `key.revoke` are deterministic on one server, but they change the keys (and so the `profiles` pins) of the five test actors for every later vector, and every vector authenticates with `k1`. They need a run of their own with an actor reserved for it.

Where the two reference servers answered differently in round 22 and the text was silent, round 23 decided (DECISIONS-r23.md F4) and the vectors now pin it: `read` with `effect` or `cursor` together with `at`, `follow` or each other is `invalid` (`F4a`), a notice for an actor with no live subscription is dropped, never replayed (`N1`), and an integer below -(2^53-1) is treated like one of 2^53 or more (`N2`, `N3`; `-(2^53-1)` itself is an ordinary number and, as a Json value, `invalid` by section 2).

**The operation files that read the state** (`06-read.state`, `11-approve`, `21-redact`) were recorded in round 23 as `read {space, after, state: true}`. `make_wire_vectors.py` rewrites each such step mechanically to the pair it became: a `state {space}` call whose reply is the state the two servers sent, wrapped as `{ok: {state}}`, then the same `read` without `state`, with the records and the `end` they sent (`split_state_reads`). That is sound because the state bytes are untouched and the script asserts that the oracle (`ref/wire.py`) produces exactly those states at that point; but these frames were never produced by a server under the new call. **Re-record them** (`interop/run.py` then `report.py`) once both servers implement `state`; until then the rewritten files are the contract.

**Generation and the pinning of receipts.** `make_wire_vectors.py` checks its oracle against the 18 golden receipts of `interop/golden/` and generates everything after them, all under the current P-01 (round 23, F1: the targets of an instruction are pinned too). The golden transcripts were re-recorded on the round-23 servers, so the operation files carry the F1 form (no `agents` in the state, the executor in a proposal's receipt `profiles`), and both reference servers pass every file.
