## Round 28 notes (spec and reference agent's choices)

- **R2: skipped, not removed.** Policy keeps the E3 candidate list as it was (unconsumed, unexpired, the rule's approvers now, `separateApprover`) and consumes the first *usable* one: a valid key and an author not guarded at the claim (`guardStatus` with the claim's pinned profiles, so `forced` comes from the profile pinned for the claim). A guarded candidate is skipped like one with a revoked key, and `relevantActors` pins it like one, because its profile is what decides. Excluding it from the list instead would make the pin list depend on profiles the first call doesn't have yet, and the fixed point of P-01 would break. The cancel right of such an approval is unchanged (P-04: it is still an approval on the effect).
- **R3: when "a guard" is judged.** The cap is decided once, when a new approval arrives, with the profiles pinned for that approval: the effect's guards are `guards_of` at that seq (the guards of `guardedFor`, and of the proposer and executor if guarded then), the same set E3 would demand at a claim made then. A guard (holding a role) skips the rule, `separateApprover` and the cap; anyone else is refused when 16 open approvals by other authors that aren't those guards exist. No flag is stored on an approval: the proposer, executor and `guardedFor` are already pinned for an approve (P-01), and an operator never changes (R4), so the set of possible guards is fixed and the bounds below hold without a state change.
- **R3: the bounds, derived.** Per author at most one unconsumed approval (supersede, and a returned one is dropped if a newer exists) and one consumed one (only the unsettled claim's stay). Authors that can never be the effect's guards hold at most 16 + 1 = 17 (the cap, plus the one rule approval a not-started outcome returns). Possible guards are the operators of `guardedFor` ∪ {proposer, executor}, at most 19. So `MAX_UNCONSUMED_APPROVALS` = 17 + 19 = **36** (bounds the E3 candidates and so `receipt.profiles`) and `MAX_APPROVALS` = 17 + 2 × 19 = **55** (bounds the effect's state item, §3). Both are in han.ts `PolicyConstants` and policy.py, derived and never checked by Policy; fuzz_fold asserts all four facts on every allowed entry (a mutant without the cap is caught as "18 approvals by authors that are never guards"). Round 27's 17/37 is gone everywhere (§2, §3, P-01, P-08, han.ts, run_wire's largest item).
- **R4.** §4.3 and P-03 say the operator is fixed by the profile's `space.create`; "operator change" is gone from §6.6, §7.5 and §11 (§11's rejected "guard stored in the session or the effect" now gives the remaining reason: the pinned profile already names it). Vector 101 is recast as `operator-withdrawal-keeps-recorded-work-waiting`: the work stays unclaimable while the operator is withdrawn, it can't approve as a guard then, and its approval made before the withdrawal counts once it confirms again (that last fact is new; the rest overlapped `outside-instructions-are-inert`). model_guard's swap move is deleted (its withdraw/confirm move already existed and is now named "confirms again"); fuzz_fold's and fuzz_diff's "operator changed" counter is now "operator confirmed again".
- **R5: leaving only.** The exception is exactly `member.set {actor: author, role: "none"}`. A guarded agent's open join (setting itself `member`) stays denied: joining is a grant, and owners admit a guarded agent (vector `guarded-agents-may-leave` pins it, which is what makes the mutation "may set its own role" non-equivalent). Leaving changes nothing recorded: the agent stays in `guarded` (sticky) and every `guardedFor` naming it stays.
- **R1 and R6 in R-24.** The strict triggers are three: an outside instruction to a guarded agent; an instruction whose author is guarded at its seq (the host reads `state {agent: <author>, at: <seq>}` as for its own agent); a `task` whose `guardedFor` is not empty (the host has the task from the records it follows). The taint is per session, recorded for every outside instruction whether or not the agent is guarded, kept in the host's own store across restarts, and makes every turn strict from the moment the agent is guarded. §8.4 and §7.5 say the same; §7.5 lists the residue (an agent delegate's proposal without the task, its subtask without a parent, any human delegate's work) and a new row for R6. Vector `delegation-carries-only-named-work` pins what Policy does carry, including a human delegate's proposal that names the task.
