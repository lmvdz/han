# Wire, sequencer and executor spec gaps (clean-room TypeScript, round 18 text)

Built from architecture.md, han.ts, goal.md, README.md, ref/README.md and the vectors only. 25 interop scenarios and a replay of 126 vectors (1,324 steps) pass against my own sequencer, but two independent implementations could still disagree on every item below. Each entry gives the section, what is missing, what I chose, and a proposed precise wording. Severity: **H** = two implementations would not talk to each other (bytes, frames, errors) or would reach different verdicts; **M** = they would talk but differ observably; **L** = behaviour a test can't pin down yet.

Items the round-18 text already settled while I was building (I re-read §3, R-16, G-01..G-05 and X-xx at the end; these used to be gaps and are now fine): `seen`/`refs` are Policy's, not the Log's (§4.1 step 3); an owner's merely-early abandon is `unavailable` + `retryAfterMs` (R-16); `read.at`; `follow` with `limit` leaves a visible gap; context blobs are served to readers of a live session (G-01); `maxClockSkewSeconds`; X-11 (back-off, tell the proposer). One of them cost me a design change, which says something: with the old text I had put a refs/seen check in the Log, and vector 126 step 5 then failed on the live server.

## 1. Connection, hello, frames (§3, §8.3, han.ts frames)

**W-01 (H) hello: bytes of `challenge`, and of `proof`.** §3 says `proof = Ed25519(key, "han-hello-v1\n" ‖ challenge ‖ "\n" ‖ dialed)` and han.ts types `challenge` as a string; §2 says every `‖` concatenates UTF-8 bytes. Not said: whether the challenge is the UTF-8 of the JSON string or the decoded bytes of an encoded value, its alphabet and length, or how the 64-byte result is written. I used the UTF-8 bytes of the string as sent, 43 base64url chars from 32 random bytes, and the proof as base64url (Sig). Proposed (§3, after the hello row): "`challenge` is 22–128 characters of `[A-Za-z0-9_-]`, fresh per connection. The signed message is the UTF-8 bytes of those characters, not a decoding of them. `proof` is the 64-byte signature, base64url without padding, like every Sig."

**W-02 (H) hello: what `dialed` is when the transport address is not the ServerName.** ServerName (§2) has no port and no scheme; the endpoint is `wss://<server>/han` or the `sequencer` URL in `/.well-known/han`. A test on localhost, or a server behind a different hostname, can't dial `han.test`. Proposed (§3): "`dialed` is the ServerName the client intends (from the space id, the actor id or the `.well-known` entry it followed), never the host or port it happens to connect to; the challenge's `server` field is the ServerName the server believes it is. A client MUST abort unless the two are equal; a server MUST sign nothing for a hello whose proof is over another name."

**W-03 (M) hello: error codes.** Unspecified: unknown actor, unknown keyId, revoked key, bad proof, wrong version, a second hello, a failed hello (does the connection stay open, may the client retry?). Chosen: unknown local actor `invalid`; unknown or revoked key and bad proof `denied`; version ≠ 1 `invalid`; a second hello `invalid`; a failed hello leaves the connection open and unauthenticated (every other call `denied`). Proposed: put these in a table in §8.3, and say a failed hello does not close the connection (or does).

**W-04 (H) Frame envelope: closedness, and answering a frame that is JSON but not I-JSON.** han.ts `RequestFrame` is `{id, call, args}`. Not said: whether extra members are invalid, whether `args` may be absent for `cancel`-like calls, what the reply `id` is for a frame that is valid JSON with a valid `id` but fails I-JSON (e.g. `1.5` inside an entry). §8.3 says unparseable frames get `{id: 0, error: invalid}`; a client that sent `id: 7` then waits forever, because the ordinary case of "my entry contains a non-integer" can't be told from "garbage". Chosen: exactly `id`, `call`, `args` (args an object); for non-I-JSON frames I answer on the request's own `id` when plain JSON parsing finds an integer one, else on 0; my client fails every in-flight call on an `id: 0` error. Proposed (§8.3): "A frame is a JSON object with exactly the members `id`, `call`, `args` (`args` an object). If it fails I-JSON but plain JSON parsing yields an integer `id`, the error reply carries that `id`; otherwise `id` 0, and a client treats an `id: 0` error as having failed every request still open."

**W-05 (M) Request ids.** "Request ids are chosen by the client" and "a streaming call whose id is still open is `invalid`". Not said: may a non-streaming id be reused while its reply is pending; must replies come in request order; may a client pipeline `append`s and are they ordered (R-07 needs entries from one actor to reach the log in send order). Chosen: frames are processed in arrival order and every call except the streams answers synchronously, so replies are in order. Proposed: "A server processes the frames of one connection in order; `append`s from one connection are ordered in the order received."

**W-06 (M) `cancel`.** han.ts: `cancel {target}` → null. Unspecified: what the cancelled stream receives (nothing? `{id, end: true}`?), and the result for a `target` that is unknown or already ended. Chosen: ok null in both cases; the cancelled stream gets no further frame. Proposed: "`cancel` of an open streaming call ends it silently and answers null. `cancel` of an id that is not open also answers null."

**W-07 (L) Upgrade details.** Path `/han`, subprotocol, `Origin`, ping/pong, idle timeouts, maximum concurrent connections, maximum message size 1.25 MiB measured on text or on decoded JSON. I set the WebSocket max payload to 1,310,720 bytes. Proposed: one sentence in §8.3 giving the path, no subprotocol, and "the limit is on the UTF-8 length of the text frame".

**W-08 (M) `Limits.maxFollows`.** Not said what it counts. I count open `read`-with-`follow`, `subscribe` and `watch` calls per connection and answer `limit` over it. Proposed: "per connection".

## 2. The pipeline and receipts (§2, §4.1, R-01…R-16)

**W-09 (H) What `receipt.profiles` contains, exactly.** P-01 lists who is pinned, but the receipt pins to profile *seqs*, and three cases have no answer: (a) the author of an entry in its OWN profile space ("the author's view is that space's own state at the entry's position"): which number goes in `profiles[author]`? (b) the server actor `@:S`, whose synthetic view has `seq: 0`: is `{"@:S": 0}` recorded? (c) a `space.create` of a profile space (author `@:S`, no state). Chosen: (a) the head before this entry (`seq − 1`); (b) yes, 0; (c) `{"@:S": 0}`. A verifier replaying my receipts has to guess the same way. Proposed (§2 Receipt and P-01): "`profiles` has one key per pinned actor. For `@:S` the value is 0. For an actor in its own profile space the value is the head before the entry (0 for the first entry). Inside a profile space that is also how Policy finds the author's view."

**W-10 (H) Server actor keys: which key signs what.** §4.3 publishes "a server's HAN keys" at `/.well-known/han`; `Receipt.homeKey` is "key in /.well-known/han"; the server actor `@:S` appends profile-space `space.create`, `key.add`, `key.revoke` and operator withdrawals "as a server actor", and its synthetic ProfileView holds "S's keys valid at the receipt time". Not said: whether the entry key of `@:S` and the receipt key are the same key set (I used one key, `srv1`), the KeyId grammar and rotation for them, and how the `from`/`until` windows map to `status: valid` in the synthetic view (is a key valid at a receipt time inside `[from, until)`? what about an entry signed by `@:S` with a key that expired a second later?). Proposed (§4.3): "The keys of `@:S` in a synthetic view are exactly the entries of S's `/.well-known/han` whose window `[from, until)` contains the receipt time; the same keys sign receipts (`homeKey`) and the entries of `@:S`."

**W-11 (H) Bootstrapping a profile space: its policy and content.** `space.create` in `profile:@x:S` needs a complete `PolicyDoc` and, per §5, content `{name}`. Nothing says what a profile space's policy is (I used visibility public, join closed, sessions nobody, extensionsMinRole owner), what `name` holds, or what Policy should do with the other fields (a verifier replays them). Also not said: who may ask the server to create a profile (registration is out of scope, but the provisioning entry is a normal entry with exact bytes). Proposed (§4.3): "A profile space's `space.create` MUST carry `policy` = the profile policy below and content `{name: <the ActorId>}`", with the policy listed, or "any valid PolicyDoc; Policy ignores it".

**W-12 (M) `/.well-known/han` and `/han-peers` JSON.** §4.3 gives `{keys: [{keyId, publicKey, from, until?, compromised?}]}`, `{sequencer: "wss://…/han", keys: […]}` and "`{server: keys}`". Not said: what `keys` is in han-peers (array like the first, or a map), the format of `from`/`until` (the Time grammar?), HTTP status and content type, caching. I served arrays of `{keyId, publicKey, from}`. Proposed: one JSON schema block for both documents in §4.3.

**W-13 (H) Step 2 and unknown spaces.** "Not home? Answer `moved` with the current home." Missing: (a) an unknown space whose id names another server: `moved` to that server, or `not_found`? (b) an unknown space whose id names us and whose first entry is not a `space.create`: Policy says `invalid` (P-16 step 4); but `read` of the same space is `not_found`; (c) the code when a sequencer declines to host a `space.create` ("by its own rules"): `denied`? `unavailable`? (d) a `space.create` for a space whose id names another server that does not host it. Chosen: (a) `moved` to the id's server, (b) `invalid`, (c) `denied`, (d) `moved`. Proposed: a four-row table under step 2.

**W-14 (M) Order of the Log's own checks, and where `limit`, `unavailable` and R-03a sit.** Step 1 dedupe, 2 moved, 3 shape, then rate limits "apply here" (inside 3). Not said: whether a rate-limited entry that is also malformed is `limit` or `invalid`; whether the R-03a "clock behind, answer `unavailable`" test comes before Policy (so a denied entry is `unavailable` while the clock catches up) or after; same for R-08's "can't reach minDurability". I check: dedupe, moved, shape, rate limit, durability, pins, signature, Policy, R-16, then the clock (invalid and denied win over unavailable). Proposed: one sentence: "verdicts that never change (`invalid`, `denied`) take precedence over `limit` and `unavailable`, which are about this moment" or the opposite, but say it.

**W-15 (H) Header size limit and what is measured.** "header JCS ≤ 16 KiB". Does the JCS include `sig`? `nonce`? I measured the whole entry including `sig`. Proposed: "the JCS of the Entry as sent, `sig` included".

**W-16 (M) `content` handling.** (a) `content: null` with `contentHash: ""`: same as absent, or `invalid`? I accept it as absent. (b) content sent with `contentHash: ""`: I answer `invalid`. (c) for kinds whose content is "—" (member.set, key.add…): any content is `invalid` (the Contents map says `null`). (d) Where is "content present iff contentHash ≠ ''" relative to R-01: a resend of a stored entry without its content returns the receipt (I do). Proposed: say (a)-(d) in step 3.

**W-17 (M) Signature step with an unknown key.** §4.1 step 5 `Identity.verify(entry, profiles[author])` and R-12 "a bad signature is `invalid`, a revoked key is `denied`". Not said: a keyId that is absent from the view (not revoked, just unknown): there is no public key to verify against. I skip verification and let Policy answer `denied` (author key not valid). Also: signatures are checked even for revoked keys (so a forged signature with a revoked keyId is `invalid`, not `denied`), and non-canonical base64url is rejected. Proposed: "An unknown keyId is `denied` (R-12); the signature of a known key, revoked or not, is checked first".

**W-18 (M) R-16 details left to the implementer.** Now mostly settled. Left: what the sequencer must remember across restart (I derive "ordered by this process" in memory and treat every replayed claim as ordered at process start, which is the stated rule); `retryAfterMs` = the larger of the two remaining waits (I chose that; the text says "the remaining wait"); whether the steady-clock wait applies to a *non-owner* abandon (no, denied) and to an executor's own report signed with the claim instance (no). Proposed: add "`retryAfterMs` is the larger of the two remaining waits".

**W-19 (M) Moves: the receiving side, and a contradiction with G-04.** §7.3 step 1 sends a `host-request` by `signal(profile:@:B, {...})`, and step 2 returns `host-accept` by signalling "the owner's profile". G-04 says a profile space accepts only G-03 notices from server actors, and only the actor itself may follow it. So neither handshake message is deliverable. Also: how B follows the space "since step 1" (a read-follow as a verifier? which `hello` identity?), how B imports a chain (the wire has no import call), what B does until `space.move` arrives, and how B publishes its key (`accept.keyId` refers to its well-known key). I built the A side only (verify `accept` against the current head with a static peer-key table, answer `moved` afterwards) and none of B's. Proposed: define the handshake as ordinary `signal`s in a dedicated space, or allow `host-request`/`host-accept` bodies in profile spaces for the listed senders; spell out B's follow with `read {follow: true}` as `@:B`, and say B starts at `n+1` with `prev = receiptHash(n)`.

**W-20 (M) Cross-server profile fetch.** §4.1 step 4 says "pin `Identity.profile(actor)`" and §4.3 "read with `read` from the HAN sequencer at `server`". For a remote actor that means my sequencer connects to theirs as `@:me` and reads a public space. Not specified: the identity it uses (the server actor, needing `hello` keys in S's well-known), caching and the 300 s freshness (R-10: fetched "within 300 s of the receipt time": measured how?), which seq is pinned when the remote head moves during the append, and what is returned when the remote server is down (`unavailable`, said). I implemented only same-server profiles and a hook for remote ones.

## 3. Reads, subscriptions, signals (§3, §8.3, G-03, G-04)

**W-21 (H) `read` details.** (a) Closedness of `args` (unknown members: `invalid`). (b) `state: true` but the reader can't read at the head (a former member): `denied` (I chose it) or `not_found` or an empty state? (c) `heads` item when `knownHeads` was sent but nothing is readable: I send `{type: "heads", heads: []}`. (d) `after` ≥ head: empty stream then `end`. (e) the order and number of `state`/`heads`/`record` items; (f) a `read` with `follow` on a space where the reader's rights end later: records they may no longer read are not sent (I check P-02 per record at fan-out). (g) `limit` + `follow` is now stated. Proposed: one sentence per item in §3.

**W-22 (H) `subscribe` versus `read` with `follow`, and who gets signals.** §8.3: "`subscribe` is called `follow` in ref/wire.py", and G-03 says notices arrive "as signal items on the actor's follow of its own profile space". han.ts `ReadItem` includes `signal` for both `read` and `subscribe`. Not said: does `read {follow: true}` deliver signals? Are they the same stream? I deliver signals on both, which means a client following by `read` receives ephemeral items in the middle of records. Proposed: "Signals are delivered only on `subscribe`" (and say a profile follow for notices is a `subscribe`), or the opposite.

**W-23 (H) `signal` has no `from`.** han.ts `signal {space, body}`; `ReadItem.signal` has `from`. G-04: "a user's server relays the user's signal to the home over its own `@:server` connection. The home accepts a relayed `from` only for actors on that server." The call has nowhere to put the relayed actor. Proposed: `signal {space, body, from?}`, where `from` is accepted only on a connection authenticated as a server actor `@:S` and only for actors `@x:S`; items delivered to followers carry `from` = that actor.

**W-24 (M) Signal fan-out.** Who receives: every follower who may read the space at its head now (I use that), including the sender (I skip the sender)? Body limits (size, depth, I-JSON integers only?), rate limit code, `signal` into a space the caller can read but that does not exist (`not_found`)? Proposed: "Signals go to every other `subscribe`r who may read the space; a body is Json under 64 KiB".

**W-25 (M) Notices (G-03) across servers.** The home "MUST send `signal(profile:<actor>, {type: "notice", space, seq})` to `S`": over what connection (`@:home` authenticated to S), what S answers if it does not host the actor, duplicates and retry (a notice is "only a hint", but is the home allowed to drop it silently if S is down?), which roles trigger it ("gives an actor a role": `member.set` to guest/member/owner; I do not notify for `banned` or `none`), and the `to` rule ("an entry whose `to` names an actor that holds a role": both `message.to` and `task.to`; `task.to` are assignees, so yes). Verification: "S reads the space as `@:S`": the notice carries no proof, so S must call back into the home with `read`; my single-server shortcut checks P-02 locally. Proposed: list the triggering roles; say delivery is best effort with a retry for 10 minutes.

**W-26 (M) Subscription visibility on a profile space.** G-04: "Profile spaces are readable by anyone, but only the actor itself may follow its profile for signals". So anyone may `subscribe` to `profile:@x` and gets records but never signals; `subscribe` of a profile space by a stranger is allowed (not `denied`). I do that. Proposed: say "a stranger's `subscribe` to a profile space receives its records only".

## 4. Blobs (§8.3, G-01, G-02)

**W-27 (H) `blobPut` part semantics.** han.ts: `blobPut {ref, offset, data}` → `{have, complete}`, "one part of at most maxBlobPartBytes, at `offset`", `have` = "bytes held so far from this uploader". Missing: are parts required in order; may they overlap (resend after a lost reply must work: R-06 style); what happens with a gap; what if a later part carries a different `ref.size` or `type`; a hash mismatch when the last byte arrives (do the held bytes survive? what code?); a part past `ref.size`; zero-length blobs; a `blobPut` after `complete` (idempotent?); `have` when bytes arrive out of order; `ref.uri`. Chosen: contiguous prefix only: `offset ≤ have` or `invalid` (gap); overlapping bytes must equal those held, else `invalid`; later parts must repeat the same `size` and `type`; a mismatch at the end discards the upload and answers `invalid`; `offset + len > size` is `invalid`; after `complete`, any repeat answers `{have: size, complete: true}`; a zero-length blob is one part at offset 0 with empty data. Proposed: these as bullets in §8.3.

**W-28 (M) `blobPut` from whom, quotas, `complete` per uploader.** "Every byte came from that uploader's own blobPut calls": uploader identity is the connection's `who`. Not said: per-uploader quota errors (`limit`), the 24 h own-blob read applies to a blob uploaded complete only, and what `complete` means when the same actor uploads from two connections concurrently (I key on actor + hash, so the second connection continues the first's progress).

**W-29 (H) `blobGet` details.** (a) Error codes: a caller without access gets `not_found` (I chose, so the answer doesn't confirm existence) or `denied`? (b) Match rule: does `ref` match a referenced BlobRef by hash only, or by hash+size+type? I use hash+size. (c) `offset`/`length`: `length` above `maxBlobRangeBytes` is clamped (I clamp) or `invalid`; `offset` > size `invalid`; `length: 0`; ranges on a blob that is still unreferenced (own 24 h rule needs a `space` for P-02: I ignore `space` for it). (d) What a server does if the stored bytes are missing though supply is claimed. (e) For a context blob (G-01 access 1, new): "live session on which `sessionAccess` grants read" — checked at call time; a reader mid-download loses access when the session closes (I check each ranged call). Proposed: items (a)-(c) in §8.3.

**W-30 (M) G-02 server-to-server blob fetch.** "A server that needs a blob it lacks calls `blobGet` as `@:server`... asks the author's server first, then the home, then any mirror." When does a server "need" a blob (on receipt of a record that references it? on the first `blobGet`?), and what does the *requested* server answer: G-01 is "evaluated for the server actor (P-02 server reads)" but supply (the author uploaded it *to this server*) is false for the author's server answering the home, unless the author's server is where the author uploaded. Not built (single server); the wording leaves the supply rule unclear for the home's own fetch.

## 5. Session streams (§6.6, G-05, T-07)

**W-31 (H) `stream` rules.** "accepted only from the session's actor, on a live session, with `n` one more than its last item (a repeat of the last item is ok)". Missing: error codes (I use `not_found` for an unknown session, `denied` for a non-actor or a dead session, `invalid` for a bad `n`/shape); "repeat of the last item" means byte-identical (JCS) or just the same `n` (I require identical, else `invalid`); what `n` is after the session is closed and a new one opened (counts per session, from 1: han.ts says so); `StreamItem.time` rules (grammar only; skew?); size 64 KiB measured as JCS; `space` must equal the session's space; does a `stream` item publish to the actor's own `watch`? Proposed: a table of codes in G-05.

**W-32 (H) `watch` behaviour.** "live items only, while sessionAccess grants watch". Missing: the initial reply (nothing until the first item), what happens when the right is removed mid-stream (I silently stop delivering and keep the call open, so it resumes if the right returns; the alternative is `{id, error: denied}` and end), when the session closes (I do not end the stream; alternative: `end`), error for a dead or unknown session at call time (`denied`/`not_found`), and whether `context` items need only `read` or both `watch` and `read` (G-05: "items of type context while it grants read"; read ⊆ watch by policy so equal). Proposed: say "removal of a right ends the watch with `denied`; `session.close` ends it with `end`".

**W-33 (L) Item delivery and the receipt race.** "The home evaluates access at the head when it delivers each item." A receipt and a `stream` call racing on different connections: what is "the head" at delivery. Fine for one process; two-process homes are undefined.

## 6. Executor (§4.5 X-01…X-11, §5)

**W-34 (H) How the executor learns `W` and the attempt number.** X-03: "`W` = `claim.window` is known to the executor without reading anything else". But the executor must put the *current* `launchWindow` into the claim (E5 denies a mismatch) and `attempt` = 1 + earlier claims, so it must read the space state (policy and effects). Fold needs every record. Proposed X-03: "To build a claim the executor needs `policy.launchWindow` and the proposal's earlier claims: it takes them from `read {state: true}` or by folding the records it follows (Policy.fold)". I fold; note E6 in my Part D (fold wants profile views).

**W-35 (H) What "first send" is.** X-02/X-04 measure from "the first send" of the claim. If the first send fails to connect, or the connection drops after the bytes left (R-06), is "first send" the first attempt on the wire (the stricter choice, I use it: the clock reading journaled before any attempt), or the last? The safety argument (§4.5 "why no launch follows an abandon") requires the first. Proposed: "the reading is taken once, before the first attempt to send, and never refreshed by retries".

**W-36 (M) Restart edge cases of X-06.** (a) `claiming` journaled, claim re-sent after restart and the sequencer answers `denied`/`invalid` (the proposal was cancelled, the executor demoted): there is no claim and nothing to report; the text says "if it has a receipt, report". I mark it `refused` and stop. (b) `launching` but no result: "look the result up in the outside system if possible": for `file.write` I treat "the file exists with the planned content" as succeeded/yes and anything else as unknown/unknown (a pre-existing identical file is a false positive). (c) a result journaled (`launched`) but the report not yet sent: I report it (the text lists only the three cases). (d) `started: "yes"` with `failed` when the launch raised: allowed. (e) what the executor does about the DEADLINE after a restart (nothing: it never launches). Proposed: add (a) and (c) to X-06.

**W-37 (M) X-04 clock and "no more than `stallBound` between the check and the launch".** Not testable by a black box and not implementable portably in a GC'd runtime; I make the check the line before the synchronous file write. The `elapsed-time clock`: Node has no CLOCK_BOOTTIME; I use `os.uptime()` (boot-based on Linux, `GetTickCount64` on Windows) and refuse other platforms. Proposed: list the platform clocks X-02 accepts, or require the executor to document which it uses.

**W-38 (M) X-07 key custody and lock.** "An instance key MUST NOT be held by two running processes... nor restored without its journal." Mechanism is private, but the test is not: a stale lock after a crash must not block restart (pid liveness check), and a copy of the key file without the journal must refuse. I bind the key to a journal id. A black-box tester can't tell a refusal from a crash. Proposed: say the refusal is a process exit with a message, so a test harness can look for it.

**W-39 (M) X-10 resolve content.** "attaching its journal and outside-system evidence": `effect.resolve.content.evidence` is ONE BlobRef. What is the blob: the raw journal file (format private), a bundle? I upload the journal as `application/x-ndjson`. A human or another executor can't interpret it. Proposed: "the evidence blob is a JSON document `{journal: [...], outside: {...}}` with the journal entries in order".

**W-40 (M) X-11 and what "tell the proposer" looks like.** `message` whose `refs` name the proposal: body `to`? I set `to: [proposer]`; content text is free. Does the message require the executor to be a member (yes, it is)? The back-off SHOULD has no constants: I use 1 s doubling to 60 s. Fine, but a message every time the executor re-evaluates would spam; I send it once per proposal per process life. Proposed: "once per proposal".

**W-41 (M) What an executor claims.** M5 says "deciding what to claim" is hidden, X-09 says "refuses (never claims) a plan it can't run or check". Not said: the order of X-09's plan-digest check relative to journaling `claiming` (I check before, and again after the receipt), whether it may claim a proposal in `awaiting-approval` (Policy denies; useless), or whether several instances of one actor race (the second claim is `denied` because the phase is `claimed`; the loser must then do nothing and journal `refused`). Proposed: one paragraph.

**W-42 (L) `file.write` is informative but its edges are interop-relevant for plan digests.** `target` normalisation (`.`, `..`, empty segments, backslashes, case), overwrite of an existing file, atomic replace, creation of parents, `args` with extra members, content encoding (UTF-8 string), size limit, symlinks. I refuse non-plain relative paths and extra `args` members, create parents, replace atomically (temp file + rename), refuse nothing about size. Proposed: three lines in §5.

**W-43 (L) Outcome cost.** A claim reserves `cost`; the executor may report `cost` (≤ reservation) or omit (settles the full reservation). The worked example reports `{USD-cent, 0}`. What an executor should report for `file.write` is not said. I omit it.

## 7. Verifier and gossip (R-14, R-15) as seen from the sequencer

**W-44 (M) What a sequencer does with `knownHeads`.** It answers heads for readable listed spaces; a client-supplied receipt that conflicts with what the server holds (same space and seq, different `receiptHash`, validly signed by this server) is an equivocation proof against the server itself: the text says verifiers handle it. Does the server, which may receive such a receipt in `hello`, have to react? I ignore the content of `knownHeads` except its space names. Also R-15's "exchange heads with at least one other verifier every 10 minutes" (server verifiers) and the in-space `GossipSignal` bodies are not built.

**W-45 (L) Entry `time` skew.** R-03a says "That one tolerance (`maxClockSkewSeconds`) applies everywhere a party compares a time with its own clock"; `Entry.time` is "informational, never a Policy input". ## 8. Storage and durability (R-03, R-04)

**W-46 (L) "Durable" for the black-box tester.** R-03's procedure says "kill -9 and power-cut": my fsync-before-reply design survives the first, the second depends on the file system. The text gives no format, rightly, but two things matter to peers: a torn last line after a crash is dropped (nothing was acknowledged), and a client's R-06 retry then re-appends and gets a fresh receipt. Both hold here. `redact` must remove content from storage "wherever honoured": append-only JSON lines can't, so I rewrite the content file atomically. R-04 and "append-only" pull in different directions; proposed wording: "append-only refers to headers and receipts; content stores may be rewritten to honour `redact`".

**W-47 (L) `durability` field and `minDurability`.** A sequencer that can only offer `local` must refuse `space.create`/`policy.set` asking for `replicated` with `unavailable` (R-08): I do, after Policy allows the entry. The text does not say whether to refuse before Policy. A `denied` policy.set that also asks for `replicated` is `denied` here.

## Round 21 notes from the TypeScript clean room (appended; resolutions are the spec agent's to mark)

Implemented from DECISIONS-r21.md D1-D14, architecture.md §3, §4.1, §4.3, §8.3 (G-01...G-11) as they stood at the end of this pass. Wire vectors: 82/82 vectors, 203/203 expectations (`run_wire_vectors.py --launch ts`). Points where the text still left a choice, and what the TypeScript took:

- **N-01 (G-08 challenge consumption).** "consumed by the first `hello` that names it, successful or not" does not say whether a `hello` with malformed args or `version` other than 1 names it. TS: those are `invalid` and do NOT consume; the challenge is consumed once the args are well formed (before the actor lookup, so an unknown actor, a bad proof and an unknown key all burn it).
- **N-02 (`host`, G-06/§7.3: what "verifies (R-14)" means for B).** R-14 needs the profile spaces of every pinned actor at the pinned seqs; B has no stated way to get them for actors of other servers during `host`. TS verifies the chain (seq, prev, receipt id, homeSig under the home's published key, receipt time monotone, content hash), folds with Policy, and checks entry signatures only for pinned profile views it can obtain (local profile spaces, `@:S` keys from peers, `remoteProfile` hook); otherwise the entry-signature check is skipped. Redaction proofs of `redacted` records are not checked. Please say whether B must refuse (`unavailable`) when it cannot obtain a pinned view.
- **N-03 (`host`: state between calls).** B keeps the received chain in memory until a record moving the space to B arrives, then writes it to its log. After a restart it forgets the partial chain and answers `have: 0`. The text does not say whether `have` must survive a restart.
- **N-04 (`host` `head`).** If `head` is given but is not the last record B holds after this call, TS answers `invalid`. The text says only "once it holds the chain through it".
- **N-05 (`host` check order).** TS checks args first (`invalid`), then server-actor authentication (`denied`), then ownership of the space. G-07 says args are checked after authentication; the order of "unauthenticated as server" versus "bad args" for `host` is therefore `denied` first by G-07, but `host` args are checked before the actor kind here. A vector for `host` from a user connection with bad args would pin it.
- **N-06 (G-04 relayed `from`).** A `from` that is itself a server actor (`@:S`) is `invalid` in TS (only users are relayed). A relayed signal is checked for read rights of `from`, not of the relaying `@:S`. Rate limiting of signals uses the same per-connection bucket as appends (`appendsPerSecond`); the text names no limit value.
- **N-07 (G-01 own upload).** "`space` is a space the caller can read (otherwise `not_found`)": TS reads this as read rights at the head. A foreign space is `moved` (step 2) before this applies.
- **N-08 (profile spaces and `subscribe`).** Any actor may subscribe to a profile space; TS delivers signals only to the profile actor's own subscription (G-04) and records to the rest.
- **N-09 (executor and `moved`).** D5/§3 say retry on `not_found` or `moved`. For `moved` the executor has only one URL; TS keeps retrying the same URL. Following `movedTo` through `/.well-known/han` is not implemented (the text says a client MUST retry a `moved` call at `movedTo`).
- **N-10 (frames).** G-07 (1) lists "an array" among the non-objects that close the connection; TS treats every non-object JSON value (array, scalar, null) the same way. An unknown `call` is answered `invalid` before authentication (G-07 order (2) before authentication), carrying its own `id`.
- **N-11 (test mode).** `node dist/seq.js` cannot be put into the G-11 test mode (no frozen clock, no provisioning, key id `srv1` not `h1`); `interop/ts_host.mjs` does it. A `--test-mode` flag set on the stock CLI is the implementation's business per G-11, but the TS CLI does not have one yet.
- **N-12 (D14 in the engine).** `settled: false` is now set where Policy creates the claim (`policy.ts`), so the folded state and the StateView agree without a wire-level fix-up.
- **N-13 (D4 layering).** Policy (`isPublicKey`) still checks only the grammar of a public key because the Policy vectors use dummy keys; the Log (step 3) rejects a non-canonical `publicKey` in `key.add` and in a profile `space.create` as `invalid`.
