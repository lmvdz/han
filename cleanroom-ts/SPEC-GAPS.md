# Clean-room TS implementation: spec gaps

(Part B below was written after the implementation compiled and BEFORE any vector was opened.)

## Part B: interpretation choices made before seeing vectors (hidden ambiguities)

Each entry: spec place, choice made (the most literal reading).

B1. Policy.decide has no `content` and no entry id. Spec says Entry has "exactly these fields" (no `id`), and `fold` needs the entry's own id for `entries`/`tasks`/`effects` keys. Choice: fold reads the id from `record.receipt.id` (fallback `entry.id`). Header shape check requires exactly the 12 fields. Which layer validates the header (Log step 3 or Policy.decide) is not stated; I validate in decide and return `invalid`.
B2. R-09/R-05 vs P-xx precedence: `invalid` (shape, unresolved refs/ids, wrong planDigest, bad result/started pair, cost with wrong started, self-operator) is returned before any `denied` check. Not stated anywhere when both apply.
B3. Which Policy checks are `invalid` vs `denied` is mostly unstated. Only these are labelled invalid: wrong planDigest / proposal not in space on approve, bad (result,started) pair, actor naming itself as operator, unknown fields. I chose `denied` for: space.create after seq 1 (P-04 table says "only at seq 1", P-11 says "only valid at seq 1"), checkpoint.through > head, wrong-kind references (e.g. task.update naming a non-task), to=[] on tasks, budget unit mismatch, keyId reuse.
B4. Missing profile in `ctx.profiles`: for the author -> `denied` (R-12: key must be `valid` in profiles[author]); for a member.set target / other actors -> treated as `human` kind, no operator.
B5. Time comparison: all ctx/entry times are fixed-width strings, compared lexicographically. "expired" means `expiresAt <= ctx.time` ("after ctx.time" is valid).
B6. roleHistory interval semantics (P-02): `{from, to}` inclusive on both ends. `from` = seq of the member.set that granted, `to` = seq of the member.set that removed. So a removed member can still read the removing entry. Not stated.
B7. canRead for server actor `@:S`: home -> true; S in deny -> false; otherwise true if some actor on S has a current readable role, or a history interval covering `seq`. A current role counts for all seqs (as for humans).
B8. P-03 agent check (`allowAgents`) applies only when *granting* a readable role (owner/member/guest), not when banning or removing. Spec says "for a target whose profile actorKind != human" without restricting the role.
B9. P-03 Owner may set own role to anything except leaving zero owners. "Self-leave: ... unless they are the last owner". Setting role=none on a banned actor by an owner is allowed. Open join only role `member` (not guest). Invite: author must be exactly `member` (owners take the owner path).
B10. P-03 "Profile spaces: owners are the actor and @:server. The only other allowed member.set is the operator's confirmation or withdrawal". Contradictory on its face (owners may set any role, so the server could confirm for the operator). Choice: in a profile space the only allowed member.set is: operator confirms (author = operator, role owner, operator is human per ctx.profiles), or withdraws (role none; author operator, the actor, or `@:server`). `roleOf` in a profile space returns "owner" for the actor and the server actor (so they can redact, etc.); `roles` state stays empty.
B11. Profile space creation: author must be `@:<server>`; `body.profile` required in profile spaces and forbidden elsewhere (both `invalid`); non-profile space creation requires the author to be a human by ctx.profiles; creator becomes owner with roleHistory `[{from:1}]`; in profile spaces `roles` is empty. Creator/home server in `policy.servers.deny` -> denied.
B12. key.add / key.revoke: author = the actor (any un-revoked key from the space's own state) or `@:server`; reusing a keyId (even revoked) -> denied; revoking an unknown or already-revoked key -> denied. Revoking one's last valid key is allowed.
B13. P-04 `redact`: no role is required of the target's author (table lists only "the target's author, or an owner"). Redact of an effect.propose whose effect is not in a final phase -> denied.
B14. P-04 `message`: owner/member/guest. `task.cancel`: sets cancelRequested, repeated cancel is allowed (only effects deny the second cancel).
B15. P-05 closing: refund goes to the nearest open budgeted ancestor *starting at the parent*, else the space; the closed task's own `left.amount` becomes 0 (state not specified). A claim's settlement refund goes to the claim's source task if still open, else the nearest open budgeted ancestor of it, else the space. An owner closing is exempt from "assignee can't close while claimed/unknown". The assignee path also requires the assignee to hold a role.
B16. P-05 budgeted task by a non-human author: needs accountability and an open budgeted parent assigned to it. "Budgeted task" accountability check applied only when `budget` is present. Unbudgeted-space task with `budget` -> denied.
B17. P-05 session.open `task`: must exist and the author must be assigned (or an owner); not required to be open.
B18. P-06 changing budget: "nothing is reserved" = no open task with a budget and no unsettled claim reservation (spent money is not "reserved"). Same unit: budgetLeft = new amount - (old amount - old budgetLeft).
B19. P-06 charging when the space is budgeted but the named task has no budget: charged to the space. The "agent must name budgeted task" rule is checked against the *proposer's* kind (at propose and at claim E6).
B20. P-08 "approvers" role entries match by exact role (an owner does NOT satisfy `["member"]`). Approver must also hold a role now. `separateApprover` applies to every approver including guards. Cap of 16: counts open (unconsumed, undropped, unexpired) approvals by authors other than the new author, excluding guards' approvals. Approval phases accepted: awaiting-approval, ready, claimed; others denied.
B21. P-08 supersession: older open approvals by the same author get `dropped: true`. After `effect.resolve failed` ("no approvals carried") every approval gets `dropped: true` (consumed ones keep `consumedBy`).
B22. P-07 E3 key check uses `ctx.profiles[approver].keys[approval.keyId]`; a candidate with no profile in ctx is skipped like a revoked key. relevantActors cannot know key validity, so it returns *all* candidates in order (deduplicated), not "up to and including the first valid". The order is author, member.set target, proposer, candidate authors, guards.
B23. P-07 E6 for budgeted spaces, charged-to computed at claim time from the effect's task.
B24. P-09 abandon: any outcome not signed by (executor, claim.instance) is an abandon; abandon needs the author to be an owner now. `A = ceil(window*101/99) + 2` computed in integers. Own `unknown` with repeatable and no cancel: claim marked settled (spent in full), phase ready; approvals stay consumed (only `started:"no"` returns them). `unknown/yes` carrying a cost: cost only validated against the reservation, not used.
B25. P-09 "at most once per claim", "for the latest claim": outcome on an older claim or a claim that already has an outcome is denied; the effect must be in phase `claimed`.
B26. P-10 resolve with `cost` and result failed -> invalid (cost only valid with succeeded).
B27. P-11 policy.set "can't deny ... the servers of every owner": read as "may not deny the server of any current owner" (alternative: may not deny all owners' servers). Reduction in `sessions` levels: read and steer must be at least as strict as watch (rank guest < member < owner < nobody).
B28. P-15 effective mode: a session whose steerMode is not in `modes` is dead if guarded; if auto it is effectively guarded when `guarded` is in `modes`, else dead.
B29. P-15 `guardedNow`: sticky `guarded[X]` first, else the guard of any live, effectively-guarded session. A session's `guard` is recorded for every non-human opener with a confirmed operator.
B30. P-15 hold mechanics: instruction paths = session.input into X's session (by anyone other than X, g), `task` naming X, `effect.propose` naming X as executor; sets `held[X]=g` and `outside[X]=seq`. Settle after every entry: for each guarded X, pending outside open tasks / unfinished effects (newer than `cleared[X]`, not authored by X or g) hold X, and record g among the effects' guards. A newly recorded guard demotes a `ready` effect to `awaiting-approval` unless g already has an open approval. (Pre-vector I excluded the effect created by the current entry, trying to reconcile the table row "ready, when P-15 records a guard" with "An executor's hold doesn't change the phase"; vector 87 forced removing that exclusion, see A8.)
B31. P-15 release: author must equal `held[owner of session]`, must hold a role, and `outside[X] <= entry.seen`; releasing sets `cleared[X] = entry.seen` and removes the hold. No sessionAccess needed. Release does not count in `steers`.
B32. P-15 unguard: `session.close` by X itself while X is not held, of a session whose steerMode is `guarded`, deletes `guarded[X]` when X has no other open `guarded` session (also when the session was already closed).
B33. P-15 held restrictions: allowed kinds = message, session.open/close, session.input (own sessions only), task.update, effect.outcome/resolve/claim/cancel, task.cancel, effect.propose. Everything else (incl. checkpoint) denied. A held proposer's new effect starts awaiting-approval with `guards=[g]`.
B34. P-15 guards of an effect = recorded `guards` + `held[proposer]` + `held[executor]` now, first two. A guard's approval is required at claim only if the guard holds a role. A guard that is also a rule approver: the same approval is consumed for both (`approval` and `guardApprovals` both list it).
B35. P-15 sessionAccess: "dead" = not live; a session actor's guard gets all three rights only on a live session while holding a role; others: current role rank >= level rank. A non-role holder gets nothing.
B36. P-15 session.open: allowed number of open sessions per actor < 64 before the new one. Guard recorded only if the opener is non-human with a confirmed operator.
B37. Extension kinds: body must be an object whose numbers are non-negative safe integers; role check by RANK against extensionsMinRole; denied for held agents.
B38. Size limits: only the header JCS <= 16 KiB is enforced in Policy; content/list/string limits are in wire.ts `validateContent`.
B39. Unspecified: `space.move` where `to` equals the current home is allowed; `checkpoint` author must be owner/member (no accountability check); `session.close` of an already closed session allowed (needed by P-15 "re-closing").

## Part A: vector-driven findings

Scores: literal implementation (full §2 header grammar enforced in `decide`): 43 of 1115 steps (3 of 111 vectors). With only the header relaxation (A1): 1096 of 1115 steps (98 of 111 vectors). After the remaining vector-driven fixes (A2..A9): 1115 of 1115 steps, 111 of 111 vectors, purity and determinism checks included (inputs deep-compared before and after, results compared across two calls). No failure was an implementation bug (IMPL 0 from vectors; one IMPL bug, a wrong start-of-walk flag in the task-close refund, was found by my own review before any vector was run). Every failure is a SPEC-GAP (9 distinct gaps, 1072 + 19 failing steps). SPEC-WRONG: 0 outright, but A1 and A4 are vectors that violate the literal §2 grammar, and A8 is a self-contradiction inside §6.

A1. SPEC-GAP (huge): who checks the header grammar, and what exactly is Policy's input. Vectors: every step (1072 steps fail with the literal grammar). Spec: "`nonce` `[a-z2-7]{26}`", "Entry = {v, space, kind, author, keyId, body, contentHash, refs, seen, nonce, time, sig} -- exactly these fields"; §4.1 step 3 "Shape: the header has exactly the `Entry` fields, each in its grammar" (a Log step); R-11 "Policy's five functions depend only on their arguments"; ref README "Policy checks no signatures". Readings: (a) `decide` also validates the header; (b) header shape is the Log's job and `decide` sees an entry that already passed it. Vectors carry entries with no `sig`, nonces like `n-C`, and an extra `id` field, so only (b) works, but the spec never says which §2 checks belong to Policy. Also `fold` needs the entry id, which is not in `Entry` (B1). Proposed wording: "`decide` is called only with an entry that passed Log step 3; it validates only the body (R-09), reference resolution (R-05) and `seen`. `fold` takes the id from `record.receipt.id`. Test vectors may omit `sig`/`nonce` and add `id`; implementations ignore them."

A2. SPEC-GAP: space.create after seq 1, denied or invalid. Vector 01-create-once#1 expects `invalid`. Spec: P-04 table "`space.create` | only at seq 1" (Allowed-authors table, so denied) and P-11 "`space.create` is only valid at seq 1" (valid, so invalid). Proposed: "A `space.create` on an existing space is `invalid`", and drop or annotate the P-04 row.

A3. SPEC-GAP: over-reservation cost is `invalid`, not `denied`. Vectors 24#8, 33#8, 34#7, 49#7. Spec P-06 "An outcome or resolve may report a cost only within its claim's reservation. With no reservation, it may report a cost only in an unbudgeted space" and P-09 "`cost` ... must be <= the reservation": no code given, while the neighbouring sentence "All other pairs are `invalid`. `cost` is allowed only with `started: yes`" is a shape-style rule. Readings: denied (state-dependent) vs invalid. Vectors say invalid, including "no reservation in a budgeted space". Proposed: "A cost above the reservation, or any cost with no reservation in a budgeted space, is `invalid`."

A4. SPEC-GAP: `space.move.accept.sig` grammar. Vectors 28#6, 28#9, 41#6/#8, 66#6/#7 (and dependent read checks 28#10, 66#7). Spec §2 "signatures are 64 bytes ... base64url" and R-09 closed shapes; the vectors use `"signature-checked-by-Log-and-mirrors"`. Same boundary problem as A1. Proposed: "Policy accepts any string for `accept.sig`; the Log and verifiers check it (§7.3)", or fix the vectors to carry real 86-character signatures.

A5. SPEC-GAP: charging someone else's budgeted task. Vector 35-agent-must-charge-its-task#8: a human member who is not an assignee proposes naming a budgeted task assigned to an agent; expected `denied`. Spec P-06: "an effect's cost goes to its named task if that task has a budget" and "an agent or service MUST name ... an open budgeted task assigned to it" say nothing about a human naming a task they are not assigned to (I had no such rule, B19). Proposed text in P-06: "A proposal naming a budgeted task is denied unless its author is an assignee of that task." Open question the vector does not answer: are owners exempt? I applied it to everyone.

A6. SPEC-GAP: key.add on a used keyId, and key.revoke of an already revoked key, are `invalid`. Vectors 38-keyid-single-use#3, #4. Spec §4.3 "KeyIds are single-use, so a revoked key never becomes valid again"; §2 "single-use per actor". No result code. Proposed: "A `key.add` whose keyId already exists in the profile (even revoked), and a `key.revoke` of an already revoked key, are `invalid`." Unanswered: revoking an unknown key (I return denied).

A7. SPEC-GAP: `policy.sessions.modes` must be non-empty. Vector 72-session-policy-shape#5 (`modes: []` expects invalid; the vector's own description says "modes is a non-empty set"). Spec §6.6 and han.ts only say `modes: SteerMode[]` and "allowed modes". Proposed: "`modes` is a non-empty list of distinct SteerModes (R-09)." (I did not enforce distinctness; untested.)

A8. SPEC-GAP (internal contradiction): executor holds and the phase. Vector 87-held-executors-need-their-guard#7: a member proposes an effect naming a guarded executor; expected phase `awaiting-approval` with the executor's guard recorded. Spec §6.4: "An executor's hold (P-15) doesn't change the phase; it adds a guard that E3 checks at claim" vs the transition-table row "ready, when P-15 records a guard on it -> awaiting-approval (any entry; until the guard approves)" and P-15 "each such effect records `g` among its guards". Readings: (1) executor guards never change the phase (E3 only), (2) any guard newly recorded on a ready effect, including a fresh proposal, sends it to awaiting-approval. Vector says (2). My pre-vector compromise (exempting the effect created by the current entry) was wrong. Proposed: delete "An executor's hold ... doesn't change the phase", or say "the initial phase ignores the executor's hold; the settle step then moves every ready effect that gained a guard to awaiting-approval unless the guard already approved".

A9. SPEC-GAP: supersession when a consumed approval is returned. Vector 94-returned-approvals-stay-superseded#8: the owner approves, a claim consumes it, the owner approves again while claimed, then the executor reports `started: no`; the returned (older) approval must be `dropped: true`. Spec P-08 "A new approval supersedes its author's open ones on the same proposal" and P-09 "the consumed approval ... returned" never say whether a consumed approval counts as "open" or what happens when the returned one meets a newer one. Proposed: "A returned approval is dropped if its author has a newer undropped approval on the same proposal."

A10. Minor: the ref README says a step may carry `predecessor` ("ctx.predecessor = that space's state"), but `PolicyCtx` in han.ts has no such field and P-13 says a fork takes nothing from its parent. My Policy ignores it and still passes vector 30. README and han.ts disagree.

## Part C: Part B choices the vectors do NOT determine

I flipped these one at a time; all 1115 steps still passed, so two conforming implementations can differ on them:
- B6 roleHistory `to` bound inclusive vs exclusive (changes `canRead` for the removing entry).
- B20 approver roles: exact match vs "at least" (does an owner satisfy `["member"]`).
- B27 "the servers of every owner": any owner vs all owners; removing the owner-server rule entirely also passes (only the home-server rule is tested).
- B8 whether the `allowAgents` check applies when banning or removing an agent.
- B13 whether a redact by the target's author needs that author to hold a role.
- B15 an owner who is also an assignee closing a task while a claim runs.
- B31 whether a release needs the guard to hold a role.
- Many invalid-vs-denied choices (B3, B12): wrong-kind references, empty `to`, profile-space member.set rules, revoking an unknown key.
Flipping B24 ("abandon needs an owner") was caught by one vector step, so that one is pinned.

## Part D: re-run against the CURRENT spec (round 18 text, 133 vectors / 1,370 steps)

Before any change, the Policy from Parts A-C scored 1,340 of 1,370 steps (121 of 133 vectors). Every one of the 30 failing steps was a place where the text moved after I wrote the first version, and every one is now settled by the spec text. After fixing them: 1,370 of 1,370 steps, 133 of 133 vectors, purity and determinism checks included. Policy was restructured to follow P-16's common steps 1-10 and its kind table literally (`decide` in policy.ts).

Resolved by spec (failing step -> the text that settles it):

- D2. 112#3 owner-servers rule. The P-16 table row says "D every current owner's server is in it"; P-11 says "can't leave every current owner on a denied server (denying some owners' servers is allowed)". My B27 read it as "any owner". Fixed.
- D3. 113#6 agent check only on grant. P-03: only when a readable role is granted to a target that "holds none (no role, or banned)". I applied it on every readable role. Fixed.
- D4. 115#7 owner who is also an assignee. The task.update row orders "allow: owner and not an assignee, final" before "D assignee, final, effect claimed/unknown". Fixed.
- D5. 116#6-#16 (9 steps) wrong-kind and missing references are `invalid`, and so is an empty `to`. P-16's definition of `invalid` ("names something that isn't there, or is there as another kind") and P-05 settle it. (Was A2/B3.) Fixed.
- D6. 117#2, #7, #8 profile spaces: `roles` holds the actor and `@:server` as owners from creation, and the actor itself cannot withdraw its operator. P-03 "Profile spaces" paragraph. (Was B10.) Fixed.
- D7. 124#7, #10 re-arm. §6.4 "Re-arm" defines it (cancelled / ready if the rule's approvals and every guard's are unconsumed and undropped / else awaiting-approval) and says a repeatable own `unknown`, a repeatable `failed`/`yes`, `started:no` and a failed resolve all use it. - D8. 126#5, #6, #7, #11 and 127#12, #15, #20 order of checks. - D9. 129#6, #8 naming a task. P-06 "Naming a task": denied unless the author is an assignee or an owner, budget or not. (Was A5.) Fixed.
- D10. 130#4 Policy must not read contentHash, nonce, header time, sig or extra header fields. R-25 states it. (Was A1.) `badHeader` now checks only v, space, kind, author, keyId, refs, seen.
- D11. 131#1 `space.create` whose policy denies its own home is `invalid`, a non-human creator is `denied`. P-03 "Creation". Fixed (order between the two when both apply: invalid first, see E2).
- D12. Missing profile in `ctx.profiles` is `invalid` (P-16 step 2, R-25), not "treat as human" (was B4). Fixed via `relevantActors` pins.
