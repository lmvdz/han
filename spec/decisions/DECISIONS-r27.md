| P1 | **Who is guarded** | X is **guarded** if it chose to be (it opened a `guarded` session: X joins the set `guarded`; this is sticky) or it is **forced** (`forceGuarded` is on and the profile pinned for the entry says X is not human; nothing is stored). Steering others is not delegation: a guarded agent may `session.input` only into its own sessions. |

## Round 27 notes (P-15 agent's choices)

- **`seen` (P1).** The header field stays: R-17 needs it to reconstruct what drove an entry, and P-16 still answers `seen` > head `invalid`. Only its P-15 role (release staleness) is gone; Policy reads it for nothing else.
- **The kind name (P6).** `agent.release {agent, unguard?}` is renamed `agent.unguard {agent}`. The kind count stays 22, the body loses a field, and no wire vector or golden transcript carries the kind, so the wire is no larger; the old name described a hold that no longer exists. `agent.release` is now an unknown kind under the reserved prefix `agent` (`invalid`, vector `agent-unguard-shape`). An unguard of an agent that is not in `guarded` is `denied`.
- **Instruction denial (P7): dropped.** No concrete attack needs it. Whatever an instruction to a guarded agent causes in the world is an effect that records the agent in `guardedFor` or needs its guard at the claim, so without a guard holding a role nothing it causes can be claimed; its turns run in the stricter mode (R-24). Kept, because it is not an instruction: an agent may open a `guarded` session only if its guard holds a role (otherwise it would make a sticky choice nobody can end).
- **The `guardedFor` bound (P2): 19, not `maxDelegationDepth` + 2.** A task chain of depth D has D + 1 authors (depths 0 … D), and an effect adds its proposer and executor, so the bound is D + 3. It is stated as the absolute 19 (D ≤ 16), because lowering `maxDelegationDepth` later does not shorten chains already made. han.ts `PolicyConstants.MAX_GUARDED_FOR` (derived, never checked). With one approval consumed per guard, an effect holds at most 17 + 20 = 37 approvals (§3, P-08).
- **`guardStatus` (P1).** It returns `{guard?, guarded, forced}` with `guarded` = the agent chose guarding or is forced, so a host checks one boolean; `forced` says which.
- **The P5 rule in code.** `decide` step 8 denies a guarded author `effect.approve`, `member.set` and a `session.input` into another's session. `policy.set`, `agent.unguard` and redacting another's entry are not listed: each already needs an owner or a guard, and both are human, so the extra check could never fire (its mutation was equivalent). P-15 states the rule as one line: a guarded author may not approve, govern or steer others.
- **Delegation (P3).** The effects that carry a delegating agent are those that name its task or a subtask. Policy can't see what drove a proposal that names no task, so R-24 makes naming the driving task a host duty, and §7.5 lists the residue.
- **The six Policy functions** stay. None became pointless: `guardStatus` is still the one call a host makes (R-24), and `relevantActors` now also pins `guardedFor` and its guards.
- **R-24 (P7).** "Once an outside instruction has entered a session's context, every later turn of that session runs strict" is a host MUST with no log state; it replaces "while held, every turn".
- **Model (P9).** `ref/model_guard.py` checks GuardApproved plus five companion properties; its approval rule names owners and BOT, so a guard's approval is never consumed as a rule approval and the ghost's bookkeeping of unused guard approvals stays exact.
- **Golden transcripts.** `python ref/make_wire_vectors.py` reports STALE GOLDEN for `06-read.state.json`, `11-approve.json` and `21-redact.json`: their recorded states carry `held` and `lastOutside` and no `guardedFor`. They must be re-recorded with interop/run.py once both servers follow.
